# --- A second ratchet lives below: per-workload CEILINGS on `clamped`. ---
#
# `clamped` counts a resolved vertex whose pre-clamp f32->16.16 conversion
# disagreed with the pixel `primitive.zig`'s `toFixed` actually clamped it
# into (see CLAUDE.md's PGXP rules and the `ps1-pgxp` skill). The clamp keeps
# the vertex correct on screen, so this is not a hit rate and is not read the
# same way: it is a RATCHET on how often the clamp has to intervene, exactly
# like the percentages above are a ratchet on how much resolves. A workload
# with no `clamped` line here WARNs instead of failing, same as one with no
# hit-rate floor above.
#
# Syntax: `clamped <workload key> <count>`, parsed by `parseClampCeilings`
# (and skipped by the hit-rate parser above, `parseFloors`, on the `clamped `
# prefix) — all four ratchets share this one file on purpose, so a workload's
# numbers are read together.
#
# THESE NUMBERS EXPLODED ON 2026-09-12 when CPU mode shipped on: nine of ten
# workloads clamped ZERO vertices before it, and croc now clamps 81,466 of its
# 199,788 resolved vertices (41%). Pinned at the measured counts because that
# is this file's rule and because a ratchet set below what HEAD measures gates
# nothing.
#
# THE COMPOSITION IS NOW MEASURED, and it was the top open question of Phase 2.
# `drift_far` and `drift_max` (reported by the sweep, NOT gated) split
# `clamped` by SIZE: how far the candidate sat from the integer vertex it
# claims to describe, measured exactly as `withinTolerance` measures it, so the
# counts compose with `pgxp_tolerance` directly. A `clamped` event is either
#   - the `f32`-representation hair: a candidate a hair BELOW its own integer,
#     which the clamp repairs by one 1/65536 tick and is entirely benign; or
#   - a candidate a whole pixel or more out, which the clamp CONCEALS inside
#     the wire's pixel rather than repairing, and which `pgxp_tolerance`
#     exists to refuse.
# `drift_far` is the second class. Measured 2026-09-12, same run as above:
#
#   workload                    resolved   clamped  drift>=1px   peak drift
#   bios-only                    137,820       166           0     0.800 px
#   crash-bandicoot-europe-edc   272,650     2,040       1,228     1.043 px
#   crash-bandicoot-warped       786,820     6,983       5,147     1.032 px
#   crash-bandicoot-2            959,715     6,869       4,136     1.045 px
#   resident-evil-usa             57,692       166           0     0.993 px
#   croc                         199,788    81,466      75,726     2.029 px
#   silent-hill-usa              970,993     7,197       6,139     1.959 px
#   mgs                           49,632     3,442           0     0.995 px
#   tr1-usa-v1-1                  95,722       559         373     1.015 px
#   spyro-the-dragon-usa       1,745,322    52,591      49,111     1.975 px
#
# WHAT IT SAYS. There is no garbage class: NO vertex in any workload drifts
# past 2.03 px, so nothing here resembles the arbitrarily-far shadow the
# tolerance knob was written against. Three workloads clamp only the hair
# (drift_far 0, peak just under 1.0). Four more peak at 1.03-1.05 px, which is
# the adjacent pixel -- an off-by-one between the float projection and the
# hardware's `MAC0 >> 16`, not a propagation error. croc and spyro are the only
# real class, reaching ~2.0 px on 93% of their clamps.
#
# AND REFUSING THEM IS NOT FREE. Re-run in-game with `tol=1.0`, which rejects
# exactly the drift_far set, croc's resolved falls 1,150,338 -> 817,838 and
# `mixed_primitives` goes 4,938 -> 111,405: `unify` snaps a WHOLE primitive
# back to integers when one of its vertices is refused, so the rejection
# un-resolves twenty times more primitives than it repairs. That is the
# 40-90% partial-coverage band this file's headline result climbed out of, and
# it is why `pgxp_tolerance` still ships off.
#
# Visually (croc, 900M instr, `explore`, A/B against `tol=0.0` so the run stays
# in lockstep) the drift_far set changes 30-62% of painted pixels on a 3D
# frame -- but the change is texture and dither sampling on 3D surfaces
# shifting by a sub-pixel. Geometry lands in the same place, 2D text is
# untouched, and no crack or displaced polygon appears. PGXP on is not worse
# than the integer baseline on any frame inspected.
#
# SETTLED 2026-09-15, and it was Phase 3's inherited question: the clamp
# protects a drifted vertex's POSITION and nothing protects its W, which
# perspective-correct texturing now reads per fragment. Measured as the same
# lockstep A/B at 1.2B instructions, crossed with ps1-trace's new
# `noperspective` flag (also lockstep -- correction is consumed at the texel
# fetch and never read back by the game). croc draws 313,319 perspective-
# correct textured triangles at tol=-1 and 6,883 at tol=1.0: refusing the
# drifted set does not protect the feature, it DELETES it, because `unify`
# clears a primitive's `w` for the same reason it clears its position. And the
# drifted W adds no artifact class of its own -- with correction on the drifted
# set changes 40.9-46.6% of painted pixels, with it off 36.6-38.2%, at the same
# per-pixel magnitudes. No swim, shear or seam on croc's large textured floors.
# The reasoning is in the `ps1-pgxp` skill; no W-specific admission test was
# built, deliberately.
#
# Measured 2026-09-12, the same run as the hit rates above.

# --- A third ratchet lives below: per-workload FLOORS on `perspective`. ---
#
# `perspective <key> <count>` — the number of textured triangles sampled
# perspective-correctly, a FLOOR rather than a ceiling: more of them is the
# improvement, where more `clamped` is the regression. Pinned at the measured
# value rounded DOWN to three significant figures, so a propagation regression
# that costs coverage shows up here as well as in the hit rate.
#
# Syntax parsed by `parsePerspectiveFloors`, and skipped by the other three
# parsers on the `perspective ` prefix. Four kinds share this one file; only
# `parseFloors`, the one UNPREFIXED kind, has to name the other three's
# prefixes to exclude them — a keyed-count parser like this one excludes them
# for free by requiring its own. A unit test in `pgxp_sweep.zig` still pins
# that none of the four read each other's lines.
#
# It answers a DIFFERENT question from the hit rate above. `resolved` counts
# vertices that got a sub-pixel POSITION; this counts triangles that got all
# three DEPTHS and so sampled their texture through them. The sweep prints it
# over `textured_triangles`, every textured triangle drawn, because a low count
# has two readings that call for opposite responses: geometry that cannot
# resolve, versus a workload that draws almost no textured triangle at all.
#
# Measured 2026-09-15, the full unfiltered sweep closing PGXP Phase 3, with the
# shipped defaults — which as of that day include TEXTURE CORRECTION ON.
#
#   workload                    perspective  of textured tris     rate
#   bios-only                             0        51,512          0.0%
#   crash-bandicoot-europe-edc       29,964        41,887         71.5%
#   crash-bandicoot-warped          104,203       167,360         62.3%
#   crash-bandicoot-2                82,118       133,172         61.7%
#   resident-evil-usa                 4,200        14,776         28.4%
#   croc                             47,272        73,718         64.1%
#   silent-hill-usa                 155,093       288,517         53.8%
#   mgs                                   0        11,210          0.0%
#   tr1-usa-v1-1                      7,705        29,101         26.5%
#   spyro-the-dragon-usa            132,655       250,388         53.0%
#
# THE TWO ZEROS ARE UNDERSTOOD, and neither is a gating defect — a zero pinned
# without understanding it would be a floor that can never fail sitting on top
# of a real bug. The DENOMINATOR is what settles them: both workloads draw
# plenty of textured triangles (51,512 and 11,210), so this is not "nothing was
# drawn". Every screen either one reaches is 2D, and a 2D vertex the game built
# itself never went through a projection, so it has no depth to carry:
#   - `bios-only` is a disc-less boot. No licence logo, and the BIOS front-end
#     is 2D however many textured triangles it uses to draw itself.
#   - `mgs` NEVER LEAVES ITS MENUS. Checked directly with ps1-trace: at 900M
#     instructions the run sits on "PRESS START BUTTON", at 1.6B on the main
#     menu, and at 2.6B on the VR mission-select screen — all 2D. Every workload
#     that does reach 3D geometry reports 26-72%. This is a workload-REACH gap
#     (the same one that keeps mgs out of the FMV-decoding MDEC coverage), not a
#     gating bug, and the line below re-pins the day a script gets it into a
#     mission.
#
# THE RATE IS NOT THE HIT RATE and must not be read like one. tr1 resolves 99.1%
# of its vertices and corrects 26.5% of its textured triangles, because the two
# count different things: a triangle needs all THREE vertices carrying a DEPTH,
# where the hit rate counts a vertex with a sub-pixel POSITION. Three by-design
# rules take depths away — `unify` clears `w` for a whole primitive when one
# vertex is unresolved, `thinPrimitive` clears it on a thin primitive that is
# ALSO mixed, and a vertex whose position was recovered without a `valid_z`
# has none to begin with. A low rate is expected on a workload heavy in 2D
# overlay; what would be a finding is a rate that DROPS without one of those
# counts moving.
#
# RE-PINNED 2026-09-25. Until then `thinPrimitive` cleared the depth of EVERY
# thin primitive (tr1: 11,140 of them, spyro: 136,303), and a quad went with
# its thin half. The thin rule guards position, never depth, so it now snaps
# the integers and keeps the depths. That took Crash 71.5% -> 100.0%, tr1
# 26.5% -> 95.8%, and every 3D workload to 90-100%; the 26-72% band quoted
# above is the pre-fix measurement. It was visible, not just a number: Crash's
# thin wall and fence quads stayed affine beside corrected neighbours, and a
# triangle crossing the 1.5 px line toggled correction frame to frame.
#
# A zero floor gates nothing. Both zero lines are kept as a record of the
# measurement, not as a ratchet.
#
# RE-PINNED AGAIN 2026-09-25, spyro only, by PGXP Phase 5 Task 9: closing
# `zig build trace-golden -- pgxp` for the first time since Task 8 added
# `bus.setPgxpDisable2d(true)` to this sweep found spyro's perspective count
# BELOW the 239000 line above (measured 231,329 of 250,388, 92.4%). No other
# workload's perspective or color floor moved.
#
# ISOLATED, not just theorised: `--filter=spyro-the-dragon-usa` with a
# temporary local `setPgxpDisable2d(false)` in `runPgxp`, everything else at
# HEAD (every other Phase 5 commit — the `snapToIntegers`/`disable_2d`
# refactor in 20c6d08 included — already applied), measures 239,314 and
# 581,045: BOTH back above their original 239000/581000 floors. `disable_2d`
# alone, not the surrounding refactor, is the cause.
#
# THE MECHANISM HAS TWO PARTS, and the drop (7,985 fewer eligible triangles,
# identically for perspective and color — see the note below `color`'s
# re-pin) is bigger than a naive per-primitive account explains. `disable_2d`
# zeroes a resolved-but-not-`all_depth` polygon's depth on every vertex, quad
# included — `flat_2d_primitives` counts 7,342 such polygons directly. But
# `unify()` runs `unifySpace`/`unifyTexturedSpace` and then `weldPrimitive` on
# every primitive, and the weld table (`Gp0Engine.weld`, keyed on integer
# screen position, shared across the WHOLE frame) is "first writer wins,
# depth included" (`weldPoint`, `gp0.zig`): a flat_2d-snapped vertex that
# reaches an integer screen position FIRST publishes `w = 0` there, and any
# LATER, otherwise fully-3D vertex from an unrelated primitive that lands on
# the same integer pixel adopts that published `w = 0`, losing a real depth it
# never lacked. Temporarily instrumented (`WeldSlot.from_flat2d`, counting a
# weld adoption where the adopting vertex's OWN `w` was `> 0` before the
# adopt): **4,988** vertices lost a real depth this way in the same run that
# measures 7,342 direct flat_2d snaps — a materially large second channel, not
# a rounding artifact, and large enough on its own to plausibly account for
# the gap between 7,342 primitives and 7,985 lost triangles once quads split
# into two triangles are counted in. Both pieces of instrumentation were
# temporary, reverted immediately after measuring, and are not in this commit.
#
# This is the expected shape of `disable_2d` (a coverage instrument here,
# never the shipped default) doing exactly what its name says to a
# resolved-but-partial-depth primitive — but the weld-adoption channel means
# it can also erase depth on a DIFFERENT primitive's vertex that was never
# itself flat_2d-snapped, which is a real interaction worth a second look
# before `disable_2d` is ever considered for anything other than sweep
# coverage. Not chased further here per the controller's ruling: re-pinned to
# the measured value; the 239000 line above is retired as of this line.

# --- A fifth and sixth ratchet live below: per-workload FLOORS on `depth` and
# `depth_clears`. ---
#
# `depth <key> <count>` — the number of POLYGONS that took the PGXP depth
# test, `Gp0Engine.PgxpStats.depth_tested` (`depth.decide`'s `check`): every
# vertex carries a depth, the depths are not all equal (a flat 2D overlay
# drawn at one projected depth is not depth-tested), and it is opaque or
# `transparent_depth` is on. A FLOOR, for the same reason `perspective` and
# `color` are: fewer tested polygons means the depth-buffer feature reaches
# less geometry. Unlike those two, it is not read against a per-triangle-class
# denominator — a depth-tested polygon can be textured, Gouraud, or flat-
# coloured; the count is absolute, exactly like the hit-rate's `resolved`.
#
# `depth_clears <key> <count>` — the number of `clear_depth` records `gp0`
# decided to emit, `Gp0Engine.PgxpStats.depth_clears`: an area-change clear
# (`clearOnAreaChange`, once a frame at the buffer flip in practice) plus a
# depth-JUMP clear (`depthBits`, mid-frame, when a newly-tested polygon's
# average W sits >= `depth.clear_threshold` (4096 W units) further than the
# last one, DuckStation's new-pass heuristic). Also a FLOOR, not a ceiling: a
# clear count that COLLAPSES is the regression here, the opposite reading from
# `clamped` — it means the clear rules stopped firing and the plane
# accumulates stale depths across passes and frames instead of resetting.
# A setting TOGGLE's reset (`Gp0Engine.setDepthMirrors` -> `resetDepth`) IS
# recorded — it emits the same `sink.clearDepth` a real clear does — but is
# NOT counted by `depth_clears`: only `clearOnAreaChange` and the jump branch
# in `depthBits` increment the stat. A toggle flip therefore cannot inflate
# this floor by itself.
#
# Parsed by `parseDepthFloors` and `parseDepthClearFloors`, each requiring its
# own prefix (`depth ` / `depth_clears `) and so excluding the other four
# kinds for free; `depth_clears ` does not start with `depth ` (the
# underscore), so the two cannot take each other's lines either. A unit test
# in `pgxp_sweep.zig` pins that.
#
# MEASURED WITH ALL THREE DEPTH SETTINGS FORCED ON (`pgxp_depth_buffer`,
# `pgxp_transparent_depth`, `pgxp_disable_2d`), exactly as `perspective` and
# `color` are measured with their own correction forced on. All three ship
# OFF; this is a coverage instrument, not a picture of the defaults.
#
# Measured 2026-09-25, the full unfiltered sweep closing PGXP Phase 5 Task 9,
# also carrying `flat_2d_primitives` (reported only, no ratchet — resolved
# primitives with no depth, drawn at integers by `disable_2d`):
#
#   workload                       depth   depth_clears   flat_2d
#   bios-only                          0              0    37,146
#   crash-bandicoot-europe-edc    89,039            149       551
#   crash-bandicoot-warped       198,774            392     1,140
#   crash-bandicoot-2            212,577            274       450
#   resident-evil-usa              8,680              1     5,828
#   croc                          39,950             79     4,304
#   silent-hill-usa               183,196            428    27,192
#   mgs                            8,680              1     5,642
#   tr1-usa-v1-1                  26,101            114     1,698
#   spyro-the-dragon-usa         501,634          1,418     7,342
#
# THE ONE ZERO IS `bios-only`, and it is the SAME zero the `perspective` and
# `color` sections above already chased with a per-opcode probe (splitting
# `shaded_triangles` by source and by whether the triangle's three vertices
# produced a non-zero `rw`): bios-only's untextured Gouraud triangles are
# "12,128 (0 with w)" and it draws zero Gouraud-textured triangles at all — no
# shaded or textured triangle in its run ever carries three depths. Confirmed
# directly for THIS counter too (temporary instrumentation splitting every
# `depthBits` call by cause, reverted after measuring): bios-only has ZERO
# polygons of ANY class — textured, Gouraud, or flat-coloured — where every
# vertex carries a depth at all, so `depth_tested` (which needs exactly that,
# on ANY polygon type) reads 0 for the same underlying reason `perspective`
